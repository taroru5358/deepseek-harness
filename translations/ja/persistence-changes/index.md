# 永続化型の変更記録

日本語 | [English](../../../docs/persistence-changes/README.md) | [中文](../../../docs/persistence-changes/README.zh.md)

> これは非公式の日本語訳です。英語版（[docs/persistence-changes/README.md](../../../docs/persistence-changes/README.md)）が正です。翻訳時点: 2026-10-31、upstream commit `ce7073d51254c26cd63b22a60835b8f948deb447`。

## 概要

このリファレンスは、承認済みの Session 永続化型の変更とその前身を調べるために使う。各レコードは互換性の決定を、生成された正確なスキーマに結び付ける。ローカルのチェックは、チェックアウト内のファイルだけを使って現在のソースと記録済みの履歴を比較する。永続化型を変更するときは、まず[レビュー・クックブック](../cookbook/reviewing-persistence-type-changes.md)から始める。

古いタグ付きバージョンについては、[プレリリース・アーカイブ](releases/index.md)を使う。これは alpha/RC の型の差分を、履歴の読解と形式の検証のために再構成するものであり、その観察結果は現在の互換性の承認として扱われない。

Session 形式ごとにまとめられた完全なスキーマには、[形式リファレンス](../../../docs/persistence-changes/historical-formats/README.md)を使う。その対象範囲はライター定数に従い、リリース・タグを持たない中間形式も含む。

<a id="files-and-ownership"></a>
## ファイルと所有権

生成された[カタログ](../../../docs/persistence-catalog.md)は読める形の宣言とダイジェストを提供し、[スキーマ・インベントリー](../../../docs/persistence-schema.json)は正規化された型を含む。ルートは、論理的な Session ヘッダー、物理的な JSONL ヘッダー行、イベント・エンベロープ、およびリポジトリが宣言するすべてのイベントを対象にする。参照される型は、影響を受ける各ルートのダイジェストに推移的に寄与する。

各 `.schema.json` ファイルは、各ノードのサブグラフ・ダイジェストの先頭 16 桁の 16 進数をキーとする 1 つのノード表を格納し、1 行につき 1 つのルート、型、またはノードを持つ。ルートと型は自身のダイジェストを通じてグラフを特定するため、型の変更は変更されたノード、その祖先、および影響を受けるダイジェストだけを書き換える。正確なテキストは生成器が所有し、検証器はそれ以外のレイアウトを拒否する。

各日付付きレコードは 4 つの兄弟ファイルを持つ:

| ファイル | 所有者 |
|---|---|
| `YYYY-MM-DD-slug.md` | `kind: persistence-change` を持つ英語の承認。1 つの機械宣言、互換性の根拠、検証のエビデンスを含む |
| `YYYY-MM-DD-slug.zh.md` | 同一の機械宣言を持つ中国語の対応ファイル |
| `YYYY-MM-DD-slug.i18n.yaml` | 生成されたバイリンガル整合性レコード |
| `YYYY-MM-DD-slug.schema.json` | 影響を受け、なお存在するルートについて生成された完全な after スキーマ |

`finalized/vN.json` は、承認された互換性ベースラインの完全なルート分類とダイジェスト、および承認されたレコードの意味ハッシュを記録する。[確定レコード](../session-format-status.md#finalization-record)はそのチェックポイントを要求する。現在の V4 スキーマは互換的に進化してよい。チェックポイントは、承認された機械宣言と after スキーマを、ライターが進んだ後も保護する一方で、散文、エイリアス、ソース位置をレコードのハッシュから除外する。

メンテナーは合意された形式を [`createPersistenceFinalizationCheckpoint`](https://github.com/deepseek-ai/deepseek-harness/blob/master/scripts/persistence-finalization.ts) で取り込み、以前のものを置き換えずに新しいバージョン名のチェックポイントを書き込み、対になる `latestFinalizedVersion` を進める。このヘルパーは、現在のスキーマが承認済みの完全な履歴と一致することを要求する。コミットする前に通常の検証器を実行する。

[レコード・テンプレート](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/skills/dsh-doc/templates/persistence-change.md)は執筆用の形式を定義する。レコードの作成はバイリンガルの散文入力を受け取り、機械宣言、スナップショット、カタログの対、整合性レコードを生成する。検証器は英語ファイルから機械宣言を一度読み取り、中国語の宣言が等しいことを確認する。宣言は影響を受ける各ルート、その前身レコード、after ダイジェスト、互換性の決定を列挙する。新しいルートには前身がなく、削除には after スキーマがなく、明示的なトゥームストーンが残る。

<a id="compatibility-rules"></a>
## 互換性のルール

検出されたすべての構造上の変更には承認が必要である。古いリーダーが承認済みデータの必要な意味を保つ場合、オプショナルの機能を不透明なレコードを保持したまま安全に無視する場合、または未対応の必須データを実行、変更、復旧時の切り詰めの前に拒否する場合は、Session バージョンを据え置く。新しいリーダーは履歴上の意味と可読性を保たなければならない。バージョンを上げるのは、安全でない解釈を有効な判別子で防げない場合に限る。未知のフィールドや値は、既存のリーダーが実際に安全に扱う場合にのみ意味を持つ。型の差分だけではその振る舞いを立証できない。[リーダー互換性の決定](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/process/2026-10-08-session-reader-compatibility-review.md)を参照のこと。

| 検出された変更 | 記録の要件 |
|---|---|
| オプショナルのイベント本体プロパティを追加する（その完全なサブツリーを含む） | `same-version` |
| 必須のイベント本体プロパティをオプショナルにする | `same-version` |
| 通常のイベント型を追加する | `same-version` |
| 既存の互換性ルールの下で古いペイロードの選択肢をすべて保持したまま、通常のイベントに数値の大きい `data.version` を追加する | `same-version` |
| before と after のスキーマが同じサポート対象ポリシーを持つ user/developer ソース・スロットに、明示的に修飾された帰属種別を追加する | `same-version` |
| オプショナルのプロパティを必須にする、必須プロパティを追加する、既存の型を変更する、またはプロパティやイベントを削除・改名する | `same-version` のための互換性レビュー、または明示的な `version-bump` |
| Session ヘッダーまたはイベント・エンベロープを変更する | `same-version` のための互換性レビュー。ヘッダー・バージョンの変更には `version-bump` が必要 |

分類器は、確立された same-version のケースと、互換性レビューを要する変更を識別する。意味上の安全性は判断できない。後者は、バージョンを上げずに記録または更新する場合、明示的な `--decision same-version` を必要とする。承認の互換性セクションは双方向の実際のリーダー動作を説明し、検証セクションは実行したチェックを記録する。同時の変更を含め、遷移全体をレビューする。明示的な `version-bump` は代わりに、それ自身の増加する `SessionHeader.version` 遷移を必要とする。same-version の決定でヘッダー・バージョンの変更を免除することはできない。確定済みのレコードは不変のままであるため、後続のレコードは承認済みの 3→4 遷移を再利用できない。

CLI は、フラグ付きの same-version レコードを生成する前に、その明示的な選択を要求する。CI は記録された `decision: same-version` を読み取り、通常の履歴、スキーマ、ヘッダー・バージョンの制約が満たされる場合に受け入れる。レコードが生成されたものでも手で編集されたものでも同様である。検証は、レコードがどのように執筆されたか、人間がレビューしたかを立証できない。レビュアーは base と head のインベントリーを [`persistence-review`](../cookbook/reviewing-persistence-type-changes.md#generate) で比較する。`--check` は現在のツリーの整合性を検証するものであり、承認で既に扱われた遷移を明らかにすることはできない。

通常のイベントは、既存のすべてのペイロード・バージョンより大きい、必須の非負整数 `data.version` を持つペイロードの選択肢を追加してよい。ただし、既存のすべての選択肢が上記の確立された same-version ルールの下で読めることが条件である。オプショナルのプロパティ追加と必須からオプショナルへの変更は、新しいバージョンに伴ってよい。保持される各選択肢は個別に比較される。その他のペイロード変更は互換性レビューを要する。古いリーダーは新しいペイロード・バージョンを拒否することがある。[カタログの承認](2026-09-20-unknown-child-catalog.md)がそのような遷移の 1 つを記録している。

抽出器は、リテラルの user または developer ロール上の core 所有ソース・プロパティに対する明示的な `@persistenceSource` 束縛を受け入れる。注釈のない型から束縛を推論することはない。プロデューサーは `MessageSourceMap` のエントリーを `@persistenceAttribution` で修飾する。修飾は、未知の種別とその JSON メタデータがプロデューサーなしで読み取りを生き延びること、およびその種別が検証、リプレイ、権限の要件を課さないことを約束する。プロデューサーは重複抑制を再開するために自身の種別を検査してよいが、他のリーダーはその投影なしで記録されたメッセージを保持し導出しなければならない。記録されたスキーマは束縛、ポリシー・バージョン、リテラルの `kind` 判別子、保持の約束、修飾済み種別の集合を保持する。インベントリー形式 2 はそれらの約束を格納し、ポリシーを束縛しない抽出は形式 1 のままである。Session 形式のバージョンは独立している。比較する両方のスナップショットは互換性のあるポリシー状態を持たなければならない。既存の種別グループは引き続き通常の構造比較を受ける。削除、印のない追加、ポリシー変更、無関係な構造上の変更は互換性レビューを要する。同じワイヤ種別を持つ複数のコンテキスト形式の選択肢は 1 つのグループを形成する。

same-version のすべての説明は、古いレコードがどのように読める状態にとどまるか、古いリーダーが新しいレコードをどう扱うかを述べる。明示的な CLI の決定を必要としない確立済みのケースも含む。ログに存在しない機能は以前の振る舞いを保たなければならない。不要な機能は無視しても安全でなければならない。必須の機能には有効な拒否シグナルが必要である。未対応機能の拒否が、破損からの復旧や末尾の切り詰めになってはならない。必須からオプショナルへの変更では、値が存在しない場合にリーダーがどう扱うかを説明する。レビュアーは振る舞いとエビデンスを評価し、チェッカーは宣言と型の分類を検証する。version-bump のレコードは[Session 形式の手順](../cookbook/adding-a-session-format-version.md)に従う。

リーダーが JSON プロパティを名前で拒否する場合、そのプロパティをオプショナルの `never` として宣言し、引数なしの `@persistenceReserved` で印を付ける。抽出器は禁止されたフィールドを保持するため、後で JSON 値を許可するには既存フィールドの型変更が必要になる。必須のプロパティや JSON 値を持つプロパティはこのマーカーを持てない。印のないオプショナルの `never` と `undefined` のプロパティは、既存の省略時の振る舞いを保つ。

<a id="history-and-limitations"></a>
## 履歴と制限

1 つのベースラインが完全な初期インベントリーを記録する。以降のレコードは、前身の after スキーマを before スキーマとして使う。検証器は、欠落した前身、循環、1 つのルートに対する重複した後継、ダイジェストの不一致、最新のレコードと一致しない現在のルートを拒否する。独立したルートは独立に進める。同じ前身への 2 つの変更は、統合後に単一の順序付き履歴を必要とする。

承認されたレコードは歴史的な遷移を記述する。後継を追加するときは、その機械宣言とスキーマ・スナップショットを保持する。未承認の終端レコードは明示的に更新できる。このコマンドは、成果物を生成する前にベースライン、依存するレコードを持つもの、チェックポイントでロックされたレコードを拒否する。検証は保持されたチェックポイントのハッシュを確認するが、チェックポイントとその権限レコードが一緒に編集されていないことを証明はしない。ベースラインを供給する Git ref、リモート・サービス、リリース済みチェックアウトは存在しない。

ダイジェストは宣言された永続化型を表し、ランタイムの検証や振る舞いを表すものではない。通常のコメント、ソース位置、エイリアス名、無害な宣言の並べ替えは影響しない。互換性の注釈は記録されたポリシーのデータであり、ダイジェストに影響する。注釈のないバージョン 1 のスナップショットは元の正規化とフィンガープリントを保つ。ポリシーを持つグラフは別のフィンガープリント領域を使う。オブジェクトのフィールド、union の選択肢、intersection のオペランド、インデックス・シグネチャは、解決後の型が同じなら並べ替えてよい。タプルの位置と数値の enum 値は引き続き意味を持つ。カタログのテキストとソース位置は変わりうるため、ダイジェストが変わらない場合に承認を追加せずに、古い成果物を再生成する。`unknown` のような不透明な型は比較できる隠れた構造を公開しない。振る舞いだけの変更と、不透明な値の内部に隠れた構造は、このメカニズムの対象外である。[決定](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/process/2026-09-11-persistence-type-history.md)がこれらのトレードオフを記録している。
