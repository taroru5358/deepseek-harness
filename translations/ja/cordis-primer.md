Cordis は DeepSeek Harness の土台にある vendored なプラグイン・フレームワークです。この入門では、[サブシステムのページ](subsystems/core.md)にある生成済みのサービス／イベント・リファレンスを読む前に、harness のプラグイン作者が必要とする Cordis の考え方を説明します。[Cordis チュートリアル](cordis-tutorial/index.md)では、同じ考え方を実際に手を動かしながらたどります。vendored ソースと同期手順は [vendor/README.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/vendor/README.md) にあります。

## 5つのアイデアで見る Cordis

- **プラグインとは Service を実装するオブジェクトです。** 省略可能な `inject` と `apply(ctx)` を持つ関数か、Cordis が現在のコンテキストにマウントしてライフサイクルを管理する `Service` のサブクラスです。
- **コンテキストはサービスのリポジトリです。** サービスは `ctx.tools`、`ctx.llm`、`ctx.sessions` のような安定した `ctx.<key>` をコンテキストから取得します。他のプラグインは、具象実装を import するのではなく、キーを通じてサービスを見つけます。
- **サービスの依存関係は `inject` で宣言します。** 必須サービスを名指ししたプラグインは、それらのサービスが存在するまで待機します。そのためロード順は手動の起動シーケンスではなく、サービスの要件として表現されます。
- **通信には型付きイベントを使います。** サービスは TypeScript の宣言マージでイベント名を宣言し、リスナーが観察するか、ラップするか、ファンアウトするか、順番に実行するか、最初の bail 値で停止するかに応じて、`emit`、`waterfall`、`parallel`、`serial`、`bail` としてディスパッチします。
- **登録は可逆な効果です。** プロンプト・セクション、ツール・スキーマ、アダプター、プロバイダー、リスナーは `ctx.effect()` または `ctx.on()` を通じてインストールされるため、リロードや teardown で予測可能に巻き戻されます。

## ディスパッチ・モード

すべてのイベントは次のいずれかのディスパッチ・モードを持ち、対応するメソッドでのみディスパッチできます。

| モード | 待機するか | ディスパッチ順序 | 戻り値があるか |
|---|---|---|---|
| `emit` | いいえ | リスナーは登録順に観察する | いいえ |
| `waterfall` | いいえ | リスナーは登録順に観察する | はい |
| `parallel` | はい | すべてのリスナーが並行してイベントを観察する | いいえ |
| `serial` | はい | リスナーは登録順に観察する | はい |
| `bail` | いいえ | いずれかが bail するまでリスナーは登録順に観察する | はい |

ディスパッチ・モードはイベントの公開コントラクトの一部です。新しい harness イベントでは `@mode` タグでそれを文書化し、生成カタログが宣言とディスパッチ箇所を照合できるようにします。

## Cordis のウォーターフォールのセマンティクス

`ctx.waterfall` は around ミドルウェアです。リスナーは `(...args, next)` を受け取ります。`next()` を呼ぶと、ラップされる可能性のある結果を次のサービスに委譲します。`next()` を呼ばずに return するとショートサーキットします。値は `next()` の戻り値を通じて伝播します。

協調的なリスナーは通常、共有のリクエストや決定オブジェクトを変更してから委譲します。リスナーは結果を完全に置き換えることもでき、下流のリスナーは置き換え後の結果だけを見ます。`prepend: true` は、リスナーが通常の登録より先に実行される必要がある場合にのみ使います。

単一決定のイベントでは、ショートサーキットが設計です。ポリシー・リスナーは決定を所有していれば `next()` を呼ばずに return でき、注記や観察だけを行うリスナーは委譲しなければなりません。

## Loader の設定

`@deepseek-ai/cordis-plugin-include` は `!!js` を式ノードに解析します。Loader はエントリーの `config`（宣言された inject が有効になった後、そのプラグインのコンテキスト `ctx.serviceName` に対して）と `disabled` フィールド（マウントを判断するたびに loader コンテキストに対して）を補間します。Include は対象が有効になるまでネストした行の式を保持します。他のエントリー・メタデータはリテラルのままです。環境がプラグインを選択する場合はオーバーレイを使います。

## 実践的なルール

振る舞いはプラグインにカプセル化します。ツール・パイプラインのイベントは `ctx.tools` に、モデルのストリーミングは `ctx.llm` に、ライブな agent の協調は `ctx.agents` に属します。インターセプトとポリシーにはイベントを、直接のケイパビリティ呼び出しにはサービスのメソッドを優先します。

すべての登録は disposer を持つべきです。`ctx.effect()` から返すか、それを代行する Cordis のヘルパーを使います。teardown の順序が重要な場合は、関連する処理を1つの effect にまとめ、破棄が意図した順序で巻き戻るようにします。
