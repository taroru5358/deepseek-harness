# ネットワークプロキシ経由で DSH を実行する

日本語 | [English](../../../../docs/user/guide/network-proxy.md) | [中文](../../../../docs/user/guide/network-proxy.zh.md)

> これは非公式の日本語訳です。英語版（[docs/user/guide/network-proxy.md](../../../../docs/user/guide/network-proxy.md)）が正です。翻訳時点: 2026-10-31、upstream commit `ce7073d51254c26cd63b22a60835b8f948deb447`。

DSH は送信リクエスト（モデル呼び出し、web 検索、ページ取得、HTTP 経由の MCP サーバー）を、標準のプロキシ環境変数で指定されたプロキシ経由でルーティングします。起動時に読み取り、他に設定は不要です。いくつかのパスは設計上または runtime の制限により直接のままです。以下「直接のままになるもの」に記載します。

## 変数をエクスポートする

```sh
export HTTPS_PROXY=http://127.0.0.1:7890
export HTTP_PROXY=http://127.0.0.1:7890
```

両方の行をシェルプロファイルに置き、すべての `dsh` 呼び出しが継承するようにするか、API キーの隣の `$DSH_HOME/.env`（既定は `~/.dsh/.env`）に置きます。エクスポートされた変数は常にそのファイルより優先されます。プロジェクト自身の `.env` はそれらを設定できません。`git clone` とともに届くため、リポジトリがトラフィックの行き先を決めることを許すのではなく、DSH は起動を拒否します。

クレデンシャルが必要なプロキシは URL で受け取ります: `http://user:password@proxy.example:8080`。DSH は URL を決して出力しません。診断は拒否した変数に言及するため、ユーザー名もパスワードもどこにも表示されません。

## ブラウザはプロキシされるのにターミナルはされない理由

これは最もよくある驚きであり、DSH 固有ではありません。すべてのソフトウェアが従う単一の「システムプロキシ」は存在しません。3つの無関係な仕組みがあります:

| 仕組み | 従うもの |
|---|---|
| OS のプロキシ設定 | Safari、ほとんどのネイティブ macOS アプリ、Chrome、Edge |
| `HTTP_PROXY` / `HTTPS_PROXY` 環境変数 | `curl`、`git`、`npm`、`pip`、DSH |
| TUN モード（仮想ネットワークインターフェース） | すべて。透過的に |

Clash などのプロキシアプリケーションの「システムプロキシ」スイッチは最初のものだけを書き込みます。ブラウザはそれを拾いますが、コマンドラインツールは決して見ません。そのため変数のエクスポートが別ステップであり、TUN モードをオンにすると変数なしで両方が動作します。

DSH は OS のプロキシ設定を読み取りません。変数をエクスポートするか、TUN モードを使ってください。

## 直接のままにするものを選ぶ

`NO_PROXY` は直接到達するホストをリストします:

```sh
export NO_PROXY=internal.example.com,.corp.example.com,registry.local
```

エントリはホストを指定し、その下のすべてのサブドメインとともに一致します。`NO_PROXY=example.com` は `api.example.com` も直接送信します。先頭の `.` または `*.` も受け付けられ、同じ意味です。エントリは `:port` を持て、`*` はすべてをバイパスします。

**CIDR 範囲は動作しません。** OS のバイパスリストには `10.0.0.0/8` や `192.168.0.0/16` のようなエントリがよく含まれますが、それらを `NO_PROXY` にコピーしても効果はありません。代わりにホスト名またはドメインサフィックスを使ってください。

`localhost` や `127.0.0.1` をリストする必要はありません。DSH は常にループバックをバイパスします。そうでなければ自身の Web UI とローカルサーバーがプロキシ経由になりループするためです。

## 知っておくべき制限

**SOCKS プロキシはサポートされません。** `socks5://` の値は起動時に報告されてスキップされ、DSH はそれを指定したスキームについて直接接続します。使用可能な `HTTP_PROXY` とともに `HTTPS_PROXY=socks5://…` を設定すると、HTTP プロキシを借りるのではなく `https:` が直接のままになります。代わりに変数をプロキシアプリケーションの HTTP ポートに向けてください。ほとんどのアプリは両方を公開しており、HTTP のものは通常隣のポート番号です。

**`ALL_PROXY` だけでも十分です。** DSH は両方のスキームでそれにフォールバックします。Node と curl でこの点が異なりますが、それでも `HTTPS_PROXY` を明示的に設定する方が明確です。

**TLS をインターセプトする企業プロキシには証明書が必要です。** プロキシに到達できるようになった後に証明書エラーでリクエストが失敗する場合は、起動前に Node を組織の CA バンドルに向けます:

```sh
export NODE_EXTRA_CA_CERTS=/path/to/corporate-ca.pem
```

Node はその変数をプロセス開始時にのみ読むため、`dsh` を実行する前にエクスポートしてください。

**DSH があなたのために実行する tool も同じプロキシに従います。** bash tool のコマンド、`git`、`gh`、子プロセスとして起動された MCP サーバーはすべてこれらの変数を継承します。子の Node プログラムは自身のインストール済み runtime を使います。Node 22.21+ と Node 24+ はこれらの変数を尊重し、古い runtime は直接接続します。プロキシ変数の1つが DSH に拒否された値（たとえば SOCKS URL）を持つ場合、Node ベースの tool も起動に失敗するのではなく直接接続しますが、`curl` と `git` はその値を引き続き読みます。

**プロキシ URL のパスワードはそれらの tool にも届きます。** `HTTPS_PROXY=http://alice:s3cret@proxy.example:8080` は通常の環境変数であるため、DSH が実行するすべてのコマンド（モデルが書くものを含む）がそれを読め、環境を出力するコマンドはパスワードを保持される出力に含めます。これはシェル内の他のすべてに対して変数がすでにそう振る舞うのと同じです。それが問題なら、プロキシにクレデンシャル不要のエントリポイントを与えるか、URL 以外の方法で認証してください。

## 直接のままになるもの

DSH のすべてのリクエストがプロキシ経由になるわけではありません:

- **このマシン上のものすべて。** ループバックは常に直接です。`localhost`、`127.0.0.0/8` 全体、`::1`、`0.0.0.0`。プロキシはローカルでしか待ち受けないサービスに有用に到達できません。
- **モデルが書くコード。** Workflow worker と Node ptc-runtime プロセスはプロキシ設定を受け取らないため、モデルが書いたスクリプトはパスワードを含む可能性のあるプロキシ URL を読めません。直接リクエストは必要なプロキシを自身で設定する必要があり、実行サンドボックスの対象のままです。
- **使用状況テレメトリー。** OTLP exporter はプロキシが設定するものではなく Node 自身の HTTP クライアントを使うため、テレメトリーは直接接続し、直接の送信がブロックされる場所では単に失敗します。DSH での操作はそれに依存しません。完全にオフにするには `DSH_TELEMETRY_MODE=DISABLED` を設定します。
- **リテラルのプライベートアドレスへの `web_fetch`。** `http://10.0.0.5/` のようなアドレスを指定する URL は、プロキシに渡されるのではなく拒否されます。プロキシ未設定時と同じ拒否です。

## 動作したことを確認する

agent にページを取得するよう依頼し、プロキシアプリケーションの接続ログを見ます:

```sh
dsh --profile headless "fetch https://example.com and tell me the page title"
```

リクエストがそこに現れない場合は、変数が DSH 自身の環境に残っていることを確認します:

```sh
env | grep -i proxy
```
