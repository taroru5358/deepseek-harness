# ポストモーテム 0003: Web agent が現在の GUI ではなく代替サーバーを検証した

## エグゼクティブ・サマリー

ある Web agent が GUI のソースを変更したが、どの URL とプロセスが自分のセッションをホストしているかを知らなかった。受け入れ確認をユーザーに委ね、次に `window.__DSH_BOOT__` の欠落による白画面があるにもかかわらず素の Vite の HTTP 200 を成功とみなし、最後には元のページがすでに再ビルドされた成果物を取り込んでいたのに、別ポートの代替 `dsh web` サーバーを検証した。修正では、現在の URL と実行モードをモデルから見えるようにし、シェルから問い合わせ可能にし、listen 前に素の Vite を拒否し、本番のリフレッシュと開発 HMR を外部状態に対して検証するようにした。

## 概要

セッションはポート 3081 の DeepSeek Harness Web GUI の内側で動いており、選択中の Workspace は空の `test/` ディレクトリだった。モデルへのリクエストは GUI もそのソースチェックアウトも、URL、プロセス、更新モードも示していなかった。リポジトリ上の手掛かりは Vite 開発スクリプト付きの `apps/web` を露出していたが、完全なブラウザ構成は `dsh web` の背後にあった。

結果としての行動は個別にはもっともらしかったが、1つの受け入れ対象を共有していなかった。ソース編集、ビルド成功、HTTP 200、注入された boot manifest、ユーザーの既存ページが、互換可能な事実として扱われた。

根拠は `session-3eb796c2-5159-4686-affe-df8719f6f987` の永続化されたイベントログであり、ヘッダーには cwd `/Users/tn.shen/Documents/deepseek-harness-gui-master/test` が記録されている。最初のリクエストヘッダーはシーケンス 6 である。ユーザーへのハンドオフ、素の Vite 起動、代替ホストの起動、boot manifest のプローブ、最初の 3081 プロセスプローブはそれぞれシーケンス 30939、31865、34309、34441、34681 である。以下のタイムラインは、後の報告から意図を再構成するのではなく、これらのイベントに従う。

## 影響

ユーザーは3つの連続する誤りを指摘しなければならなかった。受け入れ確認がユーザーに押し戻されたこと、提案されたプレビューが白紙ページだったこと、成功したと報告された URL がユーザーの使っているページではなかったこと。管理されていない代替サーバーも、ユーザーが指摘するまで turn を越えて残った。

この調査のどの変更も、読み取り専用の 3081 と 3082 のトライアルサービスを再起動・変更していない。

## タイムライン

- turn 2 でテーマを編集した後、agent のシーケンス 30939 のメッセージは、ユーザーに `pnpm run demo:tui` を実行するか、指定されていない Web アプリケーションを開くよう伝えた。組み立て済み Web の受け入れ確認は実行していない。
- turn 3 で、agent は `apps/web/package.json` を読み、シーケンス 31865 でポート 5173 に素の Vite を起動し、HTTP 200 を観測して成功を宣言した。ブラウザ側では `client-modules: window.__DSH_BOOT__ is missing or not an object` が throw され、白紙ページが描画された。
- turn 4 で、agent は完全な `dsh web` 経路を見つけ、シェルを再ビルドし、シーケンス 34309 でポート 3334 に管理されていないプロセスを起動し、シーケンス 34441 でこの代替が boot manifest 付きで 200 を返すことだけを確認した。ポート 3081 は一度もプローブしなかった。
- turn 5 で、ユーザーはシーケンス 34556 で 3081 がすでに新しいテーマを表示していると報告した。agent が既存プロセスを調べて冗長なサーバーを削除したのは、その後のシーケンス 34681 になってからだ。

## 根本原因

Web の組み立てには、現在の GUI、正規 URL、実行モードについてモデルから見える identity がなかった。セッションの cwd はユーザーが選択した Workspace を正しく示していたが、モデルはそのプロジェクトディレクトリをアプリケーションディレクトリとみなした。GUI のソースチェックアウト、ビルド成果物、配信プロセス、対象 origin、ブラウザでの受け入れ確認を結び付ける永続的な記録がなかった。

素の Vite が HTTP 200 を返したため、誤った起動経路は正当に見えた。`window.__DSH_BOOT__` は完全なホストだけが注入するので、トランスポートの準備完了はアプリケーションの準備完了を意味しない。最初のリグレッションテストはこの誤りを別の形で繰り返した。タイムアウトが Vite を終了させ、非ゼロ終了の assert を満たしてしまったのだ。実際の再現により、この偽陽性が露呈した。

バックグラウンドプロセスのセマンティクスもシェルの `&` で迂回されたため、ジョブの identity、完了通知、回収、クリーンアップが適用されなかった。したがってポート 3334 の検証は、2つ目のサービスが動いたことだけを証明していた。

## 追加したガードレール

- Web ランチャーは、ログに記録される `app:web-surface` プロンプトセクションと管理された `$DSH_WEB_URL` 環境変数で、正規のループバック URL を公開する。
- 本番のガイダンスでは、成果物を再ビルドし、リフレッシュ後に既存の URL を検証することを求める。開発のガイダンスでは、HMR レシーバーが常に有効であることを説明する。同じチェックアウトでの `pnpm run dev:web` はクライアントプラグインのバンドルを再ビルドしてリフレッシュ不要のリロードを可能にするが、シェルと通常のパッケージの変更には依然としてリフレッシュが必要である。
- `apps/web` のスタンドアロン Vite serve モードは設定時に拒否する。そのサブプロセステストは自然終了を証明し、`Server.listen()` に計装して一時的な bind が見過ごされないようにする。
- 層状の実経路テストが、CLI リクエスト、本番／開発のプロンプトの厳密な内容、シェルの実行時事実、同一ポートでの静的置換、ソースウォッチャーによる再ビルド、ホストの stat ポーリング、ページ identity が変わらない状態でのブラウザ HMR を対象とする。
- PR のエビデンスは、元の 3081 セッションのスクリーンショットと、実モデルによる GUI の変更前／変更後の実行を保存している。外部のブラウザ、HTTP、プロセス、セッションログの観測が受け入れ確認を担保する。

## 教訓

- agent がユーザーを導くには、隠れた実行時の前提を知っていなければならない。起動モードはアプリケーションのコンテキストであり、属人的な知識ではない。
- HTTP の準備完了、ビルド成功、boot manifest は別々の事実である。受け入れ確認は正確な origin を名指しし、そこで要求された変更を外部から観測する。
- 代替サービスは既存ページが変わったことを証明できない。長時間実行プロセスは、実際に要求されたときに管理されたタスクライフサイクルを使う。
- リグレッションテストは、報告されたメカニズムに対して失敗できなければならない。プロセスのタイムアウトは fail-fast と等価ではなく、終了後のポート可用性はポートが一度も bind されなかったことを証明しない。
