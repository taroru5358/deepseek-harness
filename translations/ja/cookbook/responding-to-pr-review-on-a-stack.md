# スタック PR チェーンをまたぐレビューへの対応

日本語 | [English](../../../docs/cookbook/responding-to-pr-review-on-a-stack.md) | [中文](../../../docs/cookbook/responding-to-pr-review-on-a-stack.zh.md)

> これは非公式の日本語訳です。英語版（[docs/cookbook/responding-to-pr-review-on-a-stack.md](../../../docs/cookbook/responding-to-pr-review-on-a-stack.md)）が正です。翻訳時点: 2026-10-31、upstream commit `ce7073d51254c26cd63b22a60835b8f948deb447`。

レビュー・コメントは依存するスタック内の複数の PR（`A ← B ← C …`）を対象にできます。そのチェーンは GitHub 公式のスタック PR 機能でリンクしたままにします。このガイドはレビュー修正の配置と伝播を所有し、[dsh-merging-stacked-prs](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/skills/dsh-merging-stacked-prs/SKILL.md) スキルはリンク・チェックと着地を所有します。

## 基本ルール

1. **PR ブランチごとに1つの worktree。** 各 PR の修正はその PR 自身の worktree で行い、並行修正がチェックアウトを共有することはありません。
2. **GitHub のスタック・オブジェクトが権威です。** ベース・ブランチは期待される依存順序を確立し、`PullRequest.stack` と `stackEntry.position` が GitHub がそれを認識していることを証明します。それらのフィールドを確認せずに、一致するブランチ・チェーンを公式スタックとして扱ってはいけません。
3. **修正は問題を導入した PR に着地し、そこからスタックを上へ流れます。** PR `B` へのコメントが `B` が導入したコードを指す場合、`B` で修正し、`B` を `C` に伝播します。`C` もそのファイルを運んでいる場合でもです。修正を下流で起こすと、`B` は未修正コードを出荷したままになり、`B` のレビュアーから修正が見えなくなります。
4. **各レビュー修正は別個のコミットのままです。** 後の rebase で OID は変わってもかまいませんが、レビュー済みの修正をブランチ履歴から amend で消してはいけません。amend してよいのは、まだプッシュされておらず、まだレビューされていない自分の作業だけです。
5. **merge-forward か rebase を意図的に選びます。** レビュー後はどちらの履歴も許されます。書き換えられたプッシュはリースで保護されなければならず、並行して進んだリモート・ヘッドを上書きするのではなく中止しなければなりません。生の `--force` は禁止です。

## スタックを通じてコメントを解決する

1. 行動する前にすべてのコメントを内容でトリアージします。主張をコードに対して検証してください。正しい症状を指摘したレビュアーでも、原因を誤診することがあります。
2. 受け入れた各指摘をその起源の PR にマップし、そこで修正します。
3. 修正されたレイヤーを、影響を受ける各子へ順番に伝播します:
   - **Merge-forward:** 修正された親ブランチを子にマージし、子を検証して、上へ続けます。進行中の各チェックポイントを保持します。
   - **ネイティブのカスケード rebase:** `gh stack rebase` を使い、書き換えられたレイヤーを検証してから `gh stack push` で公開します。または `gh stack sync` を使います。これは先に公開する可能性があるため、[dsh-pre-push-checks](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/skills/dsh-pre-push-checks/SKILL.md) の下で同期直後の検証が必要です。
4. 委譲された修正は信頼しつつ検証します。サブエージェントの報告は意図を述べるもので、着地した内容とは限りません。実際のツリーでゲートを自分で再実行し、回帰ガードについては未修正コードで FAIL することを証明します（回帰を導入し、赤くなるのを見て、元に戻す）。両方向で通るガードは何もガードしていません。問題をすでに処理済みと再定義するサブエージェントは、自分で掘り下げるべきシグナルです。
5. トップレベルのコメントではなく、レビュー・スレッド（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`）で返信し、修正とそれを運ぶ現在のコミットまたはヘッドを述べます。
6. 書き換えられたプッシュの後は、未解決スレッド、承認、マージ可能性、チェックを読み直します。force-push されたコミット OID や古いインライン・アンカーは、指摘が解決したままであることの現在の証拠にはなりません。
7. 公式のスタック手順を通じてのみ着地します。PR がまだリンクされていない場合、着地スキルは同一作者のチェーンを自動的にリンクし、混在する作者をリンクする前に確認し、ネイティブのスタック・サポートが利用できない場合はハードストップします。

## 検証

- 修正された各 PR の現在の diff が、問題を導入したレイヤーに意図された修正を含む。
- GraphQL が期待される順序で1つの公式スタックを報告し、親に対する各子の diff がその子の変更だけを示す。
- 未解決スレッド、承認、マージ可能性、チェックが、書き換えられた各プッシュの後に再監査された。
- 関連するゲートが、スタックの先頭だけでなく、影響を受けるすべての PR で通っている。
