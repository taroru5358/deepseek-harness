# dsh-code-review スキルのメンテナンス

> これは非公式の日本語訳です。英語版（[docs/cookbook/maintaining-dsh-code-review.md](../../../docs/cookbook/maintaining-dsh-code-review.md)）が正です。翻訳時点: 2026-10-31、upstream commit `ce7073d51254c26cd63b22a60835b8f948deb447`。

[`dsh-code-review`](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/skills/dsh-code-review/SKILL.md) スキルは、指定された1人のオペレーターがプライベートな定期メンテナンス・ツールを実行して最新に保ちます。このクックブックは、そのオペレーター — および役割を引き継ぐ人 — と、スキル更新が一度限りの監査ではなく小さな定期 PR として届く理由を知りたいリポジトリのコントリビューターのための入口です。ワークフロー自体は[人によるレビューのスキル・メンテナンス Agent Note](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/proposed/process/2026-07-13-human-review-skill-maintenance.md)に規定されています。

## メンテナーが受け取るもの

オペレーターはラッパーを手動で、毎日は UTC 2日間のオーバーラップ付きで呼び出します。手動の週次復旧実行は7日間のウィンドウを使います。ワークフローは次のとおりです:

1. 選択したウィンドウ（毎日のケイデンスでは既定の UTC 2日間、週次では7日間）にマージされ、マージ・コミットが `origin/master` から到達可能な PR を選択します。マージ・コミットに到達できない PR（親が squash されたスタック・ブランチ）や、250コミットの取得上限を超える PR は `skipped-pulls.json` に記録され、実行を中止せずにスキップされます。
2. マージ前の人間レビュー・フィードバックをコミット・アンカー付きで収集し（インライン・コメントとレビュー提出）、フィードバック時点のパッチと最終的に着地した PR パッチを比較します。現在の GitHub の状態では force-push に安全なフィードバック時点のベースラインを得られないため、PR の会話コメントは取得しません。また、ターゲット・ブランチのみの変更は採用証拠から除外します。
3. 独立に設定された2つのレビュアー・アダプターが、各項目を誰が書いたか、変更がそれを採用したかを分類し、合意して採用された項目を現在のスキルに対して分類します。
4. プライマリ・アダプターが完全な改訂版 `SKILL.md` の草稿を作成し、両方のアダプターが同じ diff をレビューし、ブロッキング指摘は両方が承認するまでループします。
5. ツールが成功を宣言する前に、候補に対して `pnpm run doc-sync` と `pnpm run lint` を実行します。

各実行はアーティファクトをオペレーターのマシンに保存します。保存された diff、候補 `SKILL.md`、プロモーション・マニフェストは `~/dsh-code-review-outputs/` 以下にタイムスタンプ名で置かれます。マニフェストはソースの master コミットとスキル blob、ソース・フィードバックの ID と URL、着地証拠の範囲、アダプターの判定、ゲート結果を記録します。アダプターごとの生の I/O はプライベートな一時ディレクトリに留まり、そのパスは通知と `~/Library/Logs/dsh-code-review-maintainer/` 以下の日次ログに書かれます。メンテナンス用 worktree 自体は毎回の実行後にクリーンに復元され、オペレーターがメンテナンス・コピーをその場で編集したくなることはありません。

## オペレーターが候補 diff で行うこと

実行が候補を生成すると、macOS 通知が `dsh-code-review-promote <timestamp>` のヒントとともに届きます。

1. **diff 自体の価値で読む。** 「レビュアーが承認した」に委ねないでください。メンテナー・コントラクトでは、オペレーターが最終決定を下します。チェックリストの肥大化、履歴的な散文、単一インシデントからの裏付けのない外挿、既存のスキルや権威あるドキュメントの内容との重複カバレッジを探します。

   ```sh
   ls ~/dsh-code-review-outputs/                         # every candidate ever produced
   less ~/dsh-code-review-outputs/2026-07-16T02-00-00Z.diff
   less ~/dsh-code-review-outputs/2026-07-16T02-00-00Z.SKILL.md
   less ~/dsh-code-review-outputs/2026-07-16T02-00-00Z.manifest.json
   ```

2. **実行アーティファクトと突き合わせる。** プロモーション・マニフェストは、提案された各ルールをソース・フィードバックと着地証拠にマップします。アダプターごとの詳細な I/O、コンセンサス、採用証拠は、実行のプライベート一時ディレクトリ（パスはログに表示）にあります。少なくとも1つの候補をスポットチェックします。リンクされた人間のコメントは、実際に追加されたルールを支持していますか。リンクされた PR は、実際にそれを採用していますか。

3. **3つのうち1つを決める:**
   - **破棄。** 保存された候補を削除します。ツールは次回の実行で、その時点の現在のスキルが言う内容の下で同じフィードバックを再検討します。

     ```sh
     rm ~/dsh-code-review-outputs/2026-07-16T02-00-00Z.{diff,SKILL.md,manifest.json}
     ```
   - **バッチ。** 更新が小さく、将来の更新と組み合わせられる場合は候補を取っておきます。ソース・スキルのチェックは引き続き適用されます。`master` が先に変わった場合は、分析を再実行するか、手動で rebase して diff を再レビューします。
   - **プロモート。** リポジトリのクリーンな `master` チェックアウトから、プロモート・ヘルパーを実行します。`master` を更新し、現在のスキルが記録されたソース blob と一致することを検証し、保存された diff を適用し、ソース・フィードバックの URL または ID、着地したコミット範囲、元の実行、チェック、オペレーターの編集を本文に列挙したドラフト PR を開きます。スキルのドリフト時には、新しいガイダンスを上書きせずに停止します。オペレーターは引き続き GitHub で PR をレビューし、マージするかクローズします。

     ```sh
     cd ~/path/to/deepseek-harness   # clean master
     dsh-code-review-promote 2026-07-16T02-00-00Z
     ```

4. **アダプター出力をそのままコミットしない。** プロモート中の小さな編集 — 文言の引き締め、ソース PR のコンテキストでしか意味をなさない例の削除、既存ルールへの折り込み — は想定内であり、ワークフローが依存する「レビュアーの判断」を保ちます。マージ前にブランチを amend してください。

## 実行が候補を生成しない場合

空でない各分類ステージが少なくとも1つの有効なアダプター結果を生成した後では、これが通常のケースです。ツールは日次ログに「候補なし」を記録し、通知を送らず（アラート疲れを避けるため）、次に進みます。スキル更新のない日は、ワークフローが正しく動作しているのであり、停滞ではありません。

## 中断とハンドオフ

メカニズムは1台のマシン上にあります。オペレーターは発生時に次の中断を処理します:

- **日次実行の欠落。** 2日間のオーバーラップ・ウィンドウが1日のスキップを自動的に補います。より長いギャップは、`DSH_CODE_REVIEW_SINCE=<Nd>` を付けてラッパーを手動実行することで回復します。オーバーラップするウィンドウは冪等です。現在のスキルにすでにあるガイダンスは `covered` と分類され、候補として再入力されません。
- **アダプター・プロバイダーの停止。** 2つのレビュアー・コマンドがバイト単位で同一の実行ファイルに解決される場合、ツールは実行を拒否します。アダプター応答がスキーマまたは id 検証に失敗する単一バッチは、バッチ・レベルでフェイル・クローズされ（バッチ内のすべての項目が unclear とマークされる）、実行は継続します。生の出力はデバッグ用に保持されます。いずれかのアダプターが操作内の空でないバッチに対して有効な結果を生成しない場合、実行は失敗し、失敗記録を書き、オペレーターに通知します。プロバイダー全体の停止を「候補なし」に畳み込むことは決してありません。
- **別のメンテナーへのハンドオフ。** 現在のものを置き換えるフォローアップ Agent Note を開きます。メカニズムをリポジトリに移すか、新しいオペレーターのプライベート設定を記録します。ツールを黙って移管してはいけません。Agent Note の Risks セクションにある「単一メンテナーのバス要因」が、ハンドオフに文書化された決定を必要とする理由です。

## オペレーターのプライベート設定がある場所

ツールのソース、レビュアー・アダプター、プロバイダー認証情報、スケジューラーはオペレーターのプライベート・インフラストラクチャであり、設計上このリポジトリの外にあります（Agent Note の「Where the mechanism lives」セクションを参照）。このクックブックと Agent Note は**ワークフローが何を保証するか**を説明します。それらの保証が**どのように**実装されるかはプライベート・インフラストラクチャの関心事です。新しいオペレーターである場合、Agent Note の `## Proposal` セクションが構築の基準となる仕様です。
