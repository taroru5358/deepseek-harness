# DSH 統一角丸標準

日本語 | [English](../../docs/ui-radius.md) | [中文](../../docs/ui-radius.zh.md)

> これは非公式の日本語訳です。英語版（[docs/ui-radius.md](../../docs/ui-radius.md)）が正です。翻訳時点: 2026-10-31、upstream commit `ce7073d51254c26cd63b22a60835b8f948deb447`。

## 概要

コンポーネントの役割とサイズに応じて一貫した角丸を選び、ネストした領域、ホバーの塗り、背景、ストロークを揃えます。この標準は、DSH Web と Desktop のボタン、セル、カード、メニュー、ダイアログ、アバターを対象とします。

<a id="scope"></a>
## スコープと権威

このリファレンスは、DSH Web と Desktop の半径スケールとそのコンポーネント・ルールを定義します。ローカルの視覚的な調整は、名指しされたコンポーネントやファミリーのスコープに留まり、グローバルのスケールを自動的に変えることはありません。

[Web UI スタイル・リファレンス](web-styling.md)が一般的なスタイリングの所有関係を定義します。共有値は [`base.css`](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/ui-theme/src/styles/base.css) に、曲線の挙動は [`corner-shape.css`](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/ui-theme/src/styles/corner-shape.css) にあります。ルールを変えるときは、テーマの実装とこの標準の両方の言語版を一緒に更新します。

<a id="radius-scale"></a>
## 半径の選び方

H は、ボーダーを含む、設計上の外側の高さを CSS ピクセルで表します。R は、ブラウザが重なる角をクランプする前の CSS `border-radius` を表します。まずコンポーネントの役割を選び、次にそのサイズの変種を選びます。幅、ラベルの長さ、偶発的な折り返し、内容の拡張が、独立してより大きな半径を選ぶことはありません。

| 役割 | 典型的な寸法や例 | 半径 | 共有トークン |
|---|---|---|---|
| 小さな詳細 | H20 未満。キーキャップ、インライン・コード、小さなコントロール | R4 | `--dsw-radius-xs` |
| コンパクトなコントロール | H20–28。小さなボタン、コンパクトなアイコン・ボタン、コンパクトなメニュー項目 | R8 | `--dsw-radius-sm` |
| 標準のコントロールまたは 1 行のセル | H32–40。ボタン、入力、セレクト、ナビゲーション行 | R12 | `--dsw-radius-md` |
| 大きなコントロールまたはグループ化された内容 | 大きなボタン、意図的に複数行のセル、ネストしたフォーム・グループ | R16 | `--dsw-radius-lg` |
| 独立した内容のカード | 設定カード、メッセージ・バブル、ガイドのエントリー・カード | R20 | `--dsw-radius-xl` |
| 主要な囲いのサーフェス | コンポーザー、ダイアログ、メインまたはフローティングのパネル | R28 | `--dsw-radius-panel` |

提案されたコントロールがこれらの帯の間に入る場合は、既存の共有サイズ変種を優先します。高さのあるカードはカードのままです。ボタンの高さを超えるという理由だけで R28 に昇格させてはいけません。複数行向けに意図的に設計された複数行のセルは R16 を使い、ラベルが折り返す通常のボタンはそのボタンの変種を保ちます。

具体的な既定値: `Button` は `sm` に H28/R8、`md` に H36/R12 を使い、アウトラインの変種も含みます。標準の H32 の入力と H36 のセレクターは R12 を使います。Workspace のファイルと New terminal のガイド・エントリーはどちらも R20 を使い、タイトルのみの変種と説明付きの変種を含みます。R28 はそれらのエントリーではなく、それらを囲むパネルやダイアログに取っておきます。コンポーザーの統計とコンテキスト占有率のトリガーは、テーマの曲線を持つコンパクト・コントロールの R8 を使い、ホバー、展開、フォーカスの状態も含みます。

コード・ブロック、diff、プレビュー・カードは R16 を共有します。変更ファイルのエントリー・カード、配信ファイルのカード、提出プランのカード、作成タスクのカード、送信前後の一般的なファイル添付カード、ホバー・プレビューのパネルです。変更ファイル、配信、提出プラン、作成タスクのカード内にある 40px のアイコン・タイルは、コンポーネント固有の例外として四隅すべてに R10 を使い、両方のテーマで同じ中立のタイル塗りとボーダーを共有します。それらのホバーの塗りも同じ輪郭を保ちます。

<a id="shapes"></a>
## トークンを再利用し、意図的な形を保つ

機能固有の形状を追加する前に、`ui-primitives` のコントロールを再利用します。固定の外側寸法には `box-sizing: border-box` を使います。塗りつぶし、アウトライン、ゴースト、ローディング、無効の変種は同じサイズと半径を保ち、ホバー、押下、選択、フォーカスの状態が半径を変えることはありません。

通常のコントロールやカードに対して、10px、14px、18px、24px のようなローカルの値を導入する代わりに、名前付きトークンを消費します。スケジュールのコントロール、Desktop のオンボーディング、アカウントの通知、ショートカットのコントロールは、パッケージが所有する形状を保ちます。[半径の例外記録](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/ui-theme/tests/expected/radius-exceptions.expected.json)は、パッケージ全体を除外するのではなく、許可されたファイル、セレクター、宣言をそれぞれ固定します。ファミリー固有のプロパティは、`--dsl-guide-entry-radius` がそうであるように、共有トークンを参照してかまいません。実際のインセットから導出された形状は `calc()` を使ってかまいません。それは追加のスケール階層ではありません。

通常の角丸サーフェスは、対応している場合、テーマの `superellipse(1.5)` 曲線を使います。`corner-shape` は継承されません。テーマが要素とその `::before`／`::after` に適用します。対応していないエンジンは通常の円弧の角を保ちます。塗りとそのアウトラインが異なる曲線になる、コンポーネント固有のスムージングを導入してはいけません。

意図的な円とカプセルを保ちます。アバターとステータス・ドットは `50%` を使い、明示的なピルと完全な丸いトラックは `999px` を使ってかまいません。そのような完全な丸めの宣言には必ず、同じルール内で `corner-shape: round` を組み合わせます。高さが小さいという理由だけで、すべてのボタンをカプセルにしてはいけません。グリフのマークや小さなトラックのような描画の細部は、確立されたローカルの形状を保ってかまいません。それらは周囲のコントロールに任意の半径を正当化するものではありません。

アバターのコンテナとその `img` はどちらも円形のままにします。`border-radius` だけを継承する画像は、明示的な `corner-shape: round` が必要か、円形のコンテナから曲線を継承しなければなりません。両方で幅と高さを等しく保ちます。アカウントのアバターのサイズは[アカウント設定](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/ui-settings-account/README.md#use-this-package)を参照してください。

端まで接するドッキング・サーフェスと隣接するセルは、共有の辺に R0 を使ってかまいません。カードに接するヘッダー、フッター、画像は、露出した外側の角だけを丸めます。すべての子を四辺で丸めるのではなく、内側の直角の接合を保ちます。

<a id="nested-hover"></a>
## ネストした形状とホバー

子の半径を変える前に、次の 3 つの配置を区別します:

| 配置 | ルール | 例 |
|---|---|---|
| 同心の円形インセット | 内側 R = max(0, 外側 R − インセット)。両方の円弧が中心を共有し、`round` を使う | 外側 R16、インセット 4、内側 R12 |
| 囲いの辺に接する塗り | 囲いが可視の角を所有する。塗りをクリップするか、一致する角を継承する | 2 つの独立したホバー領域を持つスプリット・ボタンのカード |
| 別のサーフェスの内側にある独立したカードまたはフォーム・グループ | 子のセマンティックな階層を選ぶ。親のパディングを機械的にすべて差し引かない | R20 の設定カード内の R16 エディター |

標準のメニューは外側 R16、4px のパディング、R12 の項目を使い、コマンド選択、タスク・メニュー、サブ agent とバックグラウンド・ジョブのメニューで露出するハイライトを含みます。ツリーの開閉用ガターはインデントを保ち、塗りつぶされたジョブ行の中のコントロールは独自のコンパクトな形状を保ちます。コンパクトなメニューは外側 R12、4px のパディング、R8 の項目を使います。共有の `SegmentedControl` は外側 R12、4px のインセット、R8 のセグメント／インジケーターを使い、`SegmentedTabs` は外側 R16、4px のインセット、R12 のセグメント／インジケーターを使います。パディングを変えるときは、インジケーターのオフセット、幅の計算、サブメニューの位置合わせ、ポインター・ブリッジを一貫させます。

半径の減算は、ネストしたスーパー楕円の公称サイズ決定ルールでもあります。同じ指数でも厳密なオフセット曲線になるわけではないため、対角の間隔は辺のインセットと異なることがあります。共有のスーパー楕円のメニューとセグメント・コントロールの扱いを保ち、厳密に等しい半径方向の間隔が必要なときは円弧を使います。

単一のクリック可能なサーフェスは、自身にホバーを描きます。接する疑似要素やオーバーレイは、可視の囲いと同じ半径と曲線を使います。背景とボーダーの間に三日月形を残す、別々に丸めた塗りを避けます。

スプリットのガイド・カードでは、共有の半径とクリップを外側のカードに置き、接する内側のボタンには直角を与えます。各ボタンは独自のホバー色を保ってかまいませんが、外側のカードが両方の塗りを 1 つの輪郭にクリップします。ドロップダウン・メニューは既存のポータルを通じて、クリップされたサブツリーの外に保ちます。外部のフォーカス・リングをクリップで消すのではなく、可視のキーボード・フォーカスの扱いを保ちます。

```css
.entry {
  border-radius: var(--dsl-guide-entry-radius);
  overflow: hidden;
}

.main,
.trigger {
  border-radius: 0;
}
```

囲いのガイドは `--dsl-guide-entry-radius: var(--dsw-radius-xl)` を設定します。外側のカードが R20 であるのに、内側のボタンに独自の R28 の端を与えてはいけません。

<a id="settings-cards"></a>
## 設定カードの素材

アカウントのプロフィール、残高、モデル・プロバイダー、プリセット、プラグインのカードは、この既定の素材を共有します。選択済み、警告、エラー、展開済みの状態は、形状を保ったまま既存のセマンティック色を使ってかまいません。

```css
.card {
  border-radius: var(--dsw-radius-xl);
  border: 0.5px solid var(--dsw-alias-settings-card-stroke);
  background: var(--dsw-alias-settings-card-fill);
}
```

テーマは、パレットのエイリアスが存在する `body` 上で、カードの塗りを `--dsw-alias-bg-layer-2` に、ストロークを `--dsw-alias-border-l4` に解決します。機能のスタイルは両方のパレットでこれらのエイリアスを消費します。ネストしたエディターは R16 と既存のモジュールの塗りを使います。アカウントの使用量／チャージのリンクは H36/R12 の Button の形状に従い、認可のボタンは共有の Button を使います。

フラットな中立のボーダーは、共有の 0.5px のヘアラインを使います。浮き上がったメニュー、ポップオーバー、ダイアログ、パネルは `border: 0` と、既存の `--dsw-elevation-*` の素材を使います。その影にはヘアラインが含まれます。そのストロークの上に 2 つ目の中立のボーダーを追加したり、タブを区別するためだけに通常の設定カードへ影を追加したりしてはいけません。セマンティックな状態色のボーダーと、既存の半透明メニューの背景の挙動を保ちます。

<a id="verification"></a>
## 適用と検証

1. 要求されたコンポーネントを、共有のプリミティブ、オーバーレイ、疑似要素、兄弟の変種と一緒に検査します。値を置き換える前に役割を分類し、1 つの古い半径のすべての出現を同じ新しいトークンに割り当ててはいけません。
2. 適切な場合は共有の所有者を変更し、その後に依存する塗り、子の角、クリップ、状態のスタイルを揃えます。独立した子のカードは独自の階層に保ちます。
3. ライトとダークの両テーマで、実際にレンダリングされた外側のサイズ、半径、曲線、塗り、ストロークを比較します。該当する場合は通常、ホバー、押下／選択、無効、キーボード・フォーカスの状態を検査し、スプリット・ボタンでは両方の半分をホバーします。狭いレイアウトと長いラベルがコンポーネントに影響しうる場合は、それらも確認します。
4. 既存の半径、corner-shape、エレベーションのスタイルシート・ガードと、最小の関連ブラウザ・シナリオを使います。半径のガードはスケール外のリテラルと未知のトークンを拒否しますが、有効なトークンがコンポーネントに適切かどうかや、2 つのレンダリングされた輪郭が揃うかどうかは判定できません。それらは視覚的に確認します。
5. 実際の差分に対して、リポジトリの検証とドキュメントの要件に従います。意図した見た目を確認した後にだけ、影響を受ける期待値を更新します。結果としてのルール、テストしたサーフェス、未検証の状態を報告します。些細なローカル調整に対して、CSS の値を繰り返すだけのテストを追加してはいけません。
